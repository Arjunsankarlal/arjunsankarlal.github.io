Building a Reverse Image Search Engine at Scale

How we indexed 7M+ digital assets using vector embeddings and achieved production-grade accuracy while keeping costs under control.

In today's digital asset management landscape, the ability to quickly find similar images across massive libraries is no longer a luxury—it's a necessity. At Target, we faced this challenge head-on with our 2D Digital Asset Management platform housing over 15 million assets.

The traditional approach of relying on third-party APIs or simple metadata matching was proving too expensive and inaccurate for our scale. We needed a solution that could:

  • Process 7M+ images efficiently
  • Deliver sub-second search results
  • Maintain >90% accuracy
  • Reduce operational costs by at least 20%

Why Vector Embeddings?

We chose vector embeddings over traditional feature extraction methods (like SIFT or ORB) because they offer:

  • Better semantic understanding of image content
  • More compact representation
  • Faster similarity search using approximate nearest neighbor algorithms
  • Easier integration with modern ML pipelines

Technical Implementation

Our pipeline consists of three main stages:

  1. Image Processing: We use a modified ResNet-50 architecture to generate 512-dimensional feature vectors for each image
  2. Vector Storage: We store these vectors in a Faiss index optimized for cosine similarity searches
  3. Search Service: A lightweight Python Flask API that accepts query images, generates their embeddings, and returns the k-nearest neighbors from our index

Results and Optimizations

After implementation, we achieved:

  • 95.2% search accuracy measured against human-validated ground truth
  • 75% reduction in cost compared to third-party API solutions
  • Average search latency of 180ms for 95th percentile queries
  • Ability to handle peak loads of 500+ concurrent search requests

Key optimizations that made this possible:

  • Batch processing of images during off-peak hours
  • Quantization of vector indices to reduce memory footprint
  • Caching of frequently accessed search results
  • Horizontal scaling of our search service across multiple AWS EC2 instances

Lessons Learned

Building this system taught us valuable lessons about balancing accuracy, performance, and cost:

  • Start with a modest vector dimension (128-256) and increase only if accuracy demands it
  • Approximate nearest neighbor algorithms like HNSW provide excellent trade-offs for large-scale search
  • Monitor index memory usage carefully—vector stores can grow unexpectedly
  • Consider implementing a fallback to text-based search for edge cases where image features are insufficient

Today, our reverse image search service handles millions of queries monthly while maintaining the performance and accuracy standards we set out to achieve. It's become a cornerstone feature of our digital asset platform, enabling designers and marketers to find the perfect assets in seconds rather than minutes or hours.
