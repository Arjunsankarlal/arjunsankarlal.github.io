Microservice Consolidation: From Three to One

A practitioner's guide to identifying consolidation opportunities and executing them without disrupting existing deployments.

Microservice architecture has become the dominant pattern for building scalable, resilient systems. However, as systems evolve, what begins as a clean separation of concerns can accumulate into operational overhead, increased latency, and unnecessary complexity. The pendulum often swings back toward consolidation—but doing it wrong can reintroduce the very problems microservices were meant to solve.

At Target, we recently consolidated three tightly-coupled microservices into a single, well-modularized service for our 2D Digital Asset Management platform. The result? 40% reduction in operational overhead, 60% decrease in inter-service latency, and simplified deployment processes—all without sacrificing the core benefits of modularity.

When to Consider Consolidation

Not all microservices should be consolidated. Look for these signals:

  • High inter-service communication: Services that constantly exchange data with each other (especially synchronous calls)
  • Shared failure domains: When services are always deployed, scaled, or fail together
  • Duplicate concerns: Similar logging, monitoring, or authentication implementations across services
  • Transactional boundaries: Business logic that frequently spans multiple services requiring distributed transactions
  • Team cognitive load: When maintaining separation creates more complexity than it solves

Our Consolidation Journey

We started with three services:

  1. Asset Ingestion Service: Handle uploads, validation, and initial processing
  2. Metadata Enrichment Service: Add tags, descriptions, and AI-generated insights
  3. Asset Publication Service: Make assets available to downstream consumers

These services communicated via REST APIs and shared a common database. Over time, we noticed:

  • 80% of asset ingestion requests immediately triggered enrichment
  • Enrichment service rarely functioned without publication service
  • Deployment coordination was required for 95% of changes
  • Debugging required tracing across all three services

The Consolidation Strategy

We avoided a "big bang" rewrite by following this approach:

  1. Phase 1: Shared Library Extraction
    • Identified common utilities (validation, formatting, database access)
    • Created a shared SDK used by all three services
    • Reduced code duplication while maintaining service boundaries
  2. Phase 2: Strategic Service Mergers
    • Combined ingestion and enrichment (highest coupling)
    • Kept publication separate for independent scaling needs
    • Used feature flags to enable gradual migration
  3. Phase 3: Final Consolidation
    • Merged publication service after validating stability
    • Introduced internal module boundaries to preserve logical separation
    • Maintained API compatibility for internal consumers

Technical Implementation Details

1. Module-Based Architecture

Instead of returning to a monolithic blob, we used:

  • Clearly defined internal modules (ingestion, enrichment, publication)
  • Explicit interfaces between modules
  • Dependency injection for testability
  • Shared configuration and logging frameworks

2. Database Refactoring

We gradually migrated from:

  • Service-specific tables with redundant data
  • To a normalized schema with clear ownership
  • Using database views for backward compatibility during transition

3. Event-Driven Communication

Where services previously used synchronous REST calls, we introduced:

  • Internal event bus for asynchronous communication
  • Retry mechanisms and dead letter queues
  • Event sourcing for audit trails

Results and Metrics

After consolidation, we measured:

  • 40% reduction in operational overhead (fewer deployments, monitoring alerts, runbooks)
  • 60% decrease in latency for asset processing pipelines (eliminated network hops)
  • 75% faster debugging (single service traces vs. distributed tracing)
  • Simplified onboarding (new engineers learn one service instead of three)
  • Reduced cognitive load during incident response

Key Lessons Learned

  1. Consolidate logically, not arbitrarily: Group by business capabilities, not technical convenience
  2. Preserve modularity internally: Use clear module boundaries to avoid monolithic complexity
  3. Plan for data migration: Schema changes require careful backward compatibility strategies
  4. Consider incremental approaches: Big bang rewrites are risky; strive for strangler fig patterns
  5. Measure before and after: Have clear metrics to validate that consolidation improved the situation
  6. Don't forget the team: Consolidation affects team structures and ownership models

When NOT to Consolidate

We also identified services that should remain separate:

  • Services with vastly different scaling requirements
  • Services owned by different teams with independent release cycles
  • Services requiring different technology stacks or runtime environments
  • Services handling isolated business domains with minimal interaction

The Balance Point

The goal isn't to minimize the number of services, but to optimize for:

  • Team autonomy and ownership clarity
  • System reliability and observability
  • Deployment frequency and safety
  • Development speed and cognitive load

Sometimes that means more services. Sometimes it means fewer. The key is regularly evaluating whether your service boundaries still serve your organization's needs—or if they've become accumulated technical debt that needs addressing.
